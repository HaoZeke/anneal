#+TITLE: Method Composition

One narrative walk of a cooperative Lennard-Jones cluster run, naming
each mechanism from [[file:catalog.org][catalog.org]] as it appears. The walk follows
=examples/lj_cluster_search.rs='s =run_capnp_catalog= function
(examples/lj_cluster_search.rs:3996-6698), which drives one replica's
=main= entry point when invoked with the =catalog= mode
(examples/lj_cluster_search.rs:1300, 2447-2456) against
=anneal_core::methods::cluster_hopping::run_with_bias_at_checkpoints=
(src/methods/cluster_hopping.rs:1179).

* Start: configuration and identity

A replica reads =CATALOG_CAMPAIGN=, =CATALOG_ENSEMBLE=, =CATALOG_REPLICA=
from the environment (examples/lj_cluster_search.rs:4030-4031, 4042-4044) and
computes the LJ system's canonical =SystemSignature= via
=crate::catalog::lj::system_signature= (src/catalog/lj.rs:163) and its
=DescriptorSpace= via =crate::catalog::lj::descriptor_space=
(src/catalog/lj.rs:140). A =CooperativeRun= is constructed for the
single local replica with its charged-work budget
(examples/lj_cluster_search.rs:4048-4052); if a coordinator endpoint is
given, a =CatalogClient= connects under the =CatalogIdentity=
(campaign, ensemble, replica, signature digest) and attaches to the run
(examples/lj_cluster_search.rs:4057-4080) -- a refused or unreachable
coordinator leaves local execution active rather than failing the run
(=RpcFallback=).

Runtime configuration is a copy of the caller's =Config= (=run_cfg=,
examples/lj_cluster_search.rs:3997, 4223), which =main= builds from
=Config::recommended(n)=, =Config::communicating(n)= or
=Config::for_cluster(n)= by the named options
(examples/lj_cluster_search.rs:1300, 1693-1701). =budget_window= is no
longer forced on: the =run_cfg.budget_window = true= assignment is
gone, and the copy keeps the caller's =budget_window=
(examples/lj_cluster_search.rs:4238), so a coordinated chain accepts
by the serial baseline's law unless the caller's configuration says
otherwise. =polish_records= is one full quench (=relax_steps=,
examples/lj_cluster_search.rs:4400), the documented few hundred extra
steps per record or visit. Two cooperative-only extensions are set
from the environment: =CATALOG_COOP_WELLS= (feed remote minima into the
featomic packing archive, on unless set to =0=) and
=CATALOG_SHARED_BIAS= (deposit remote minima into this chain's own
well-tempered bias, off unless set to =1=)
(examples/lj_cluster_search.rs:4282-4292).

* The hop loop

=run_with_bias_at_checkpoints= (src/methods/cluster_hopping.rs:1179)
drives the ordinary perturb-quench chain against a =BasinBias= keyed on
=ClusterFingerprint= (examples/lj_cluster_search.rs:4501-4506), calling
back into the closure below every =checkpoint_interval= charged
evaluations (default 500, or =CATALOG_SLICE= / =BANK_SLICE=,
examples/lj_cluster_search.rs:4401-4406). Inside each hop, before the
checkpoint fires:

- *Move selection*: =MoveLibrary::LeanBurst='s kernels
  (src/methods/cluster_hopping/moves.rs:119-127) are chosen per hop by the
  Thompson/depth/contextual allocators (=allocate_moves=,
  =depth_reward=; catalog.org "learned allocation").
- *Screening*: the Bayesian cost-asymmetric screen and the quench
  predictor decide whether a partial relaxation is worth finishing
  (catalog.org "local search"); the return screen aborts trials
  heading straight back into the current basin.
- *Acceptance*: the Metropolis/budget-window temperature and the
  well-tempered basin bias jointly decide whether the quenched trial
  becomes the new live state; a tabu quarantine can refuse a return to
  a stalled funnel outright.
- *Stall response*: if the chain has gone longer without improving than
  its own longest prior quiet stretch, a soft-mode climb, symmetrise,
  path attempt, trail-on-stall, or restart-on-stall may fire, in that
  priority determined by the config flags set on this run.

None of this loop body talks to the coordinator; it is the same code
path a solo (non-cooperative) run takes. The cooperative layer only
enters at a checkpoint boundary.

* Checkpoint: conversation with the coordinator

The closure passed as =checkpoint= (examples/lj_cluster_search.rs:4649)
receives a =ChainCheckpoint= (src/methods/cluster_hopping.rs:156), a
read-only snapshot of the live chain's current state, best state, and
every quench boundary and accepted transition since the last
checkpoint. It runs, in order:

1. *Charge the cooperative ledger.* Every quench boundary in the
   snapshot is charged as =ChargeKind::BasinEscape=
   (examples/lj_cluster_search.rs:4868-4874); any remaining charged
   work not accounted by a boundary is =AuxiliaryEvaluation=
   (examples/lj_cluster_search.rs:4875-4886), and the batch enters the
   ledger through =CooperativeRun::record_work_batch=
   (examples/lj_cluster_search.rs:4885-4887). Boundaries are no longer
   split into =ChargeKind::AcceptedQuench= and =RejectedQuench=: both
   kinds remain in the ledger, but the checkpoint charges neither. This is
   =crate::cooperative_search::ledger::CooperativeLedger= (catalog.org
   "cooperative ledger and charge kinds") -- idempotent, so a retried
   checkpoint after a transient RPC failure never double-charges.

2. *Register local-topology evidence.* =adaptive_catalog_operations=
   (examples/lj_cluster_search.rs:4915-4923) turns the snapshot's
   accepted diagnostic probes (accepted transitions with action
   =probe= that were not adopted, examples/lj_cluster_search.rs:4911-4916)
   into =RegisterCurrent= / =Adopt= operations posted to
   =CooperativeRun::post_record_current= / =post_record_transition=
   (examples/lj_cluster_search.rs:4928-4956), building the same
   append-only transition evidence
   =crate::transition_graph::TransitionGraph= consumes elsewhere.

3. *Offer validated candidates.* Every validated quench boundary with a
   retained gradient is turned into a =CatalogCandidate= by
   =lj_catalog_candidate= (examples/lj_cluster_search.rs:7100-7110), and
   the lowest-energy one not offered before is offered to the
   coordinator via =CooperativeRun::post_offer_candidate=
   (examples/lj_cluster_search.rs:5032-5040), one offer per
   checkpoint. The coordinator runs
   candidate validation (=CandidateValidator=, catalog.org "system
   signature and candidate validation") and, if it passes, attempts
   admission into =BasinCatalog= (catalog.org "active basin catalog")
   -- same-basin improvement, conflict-set replacement, or
   capacity-replacement of the worst nonincumbent.

4. *Service the population barrier.* Before any local policy decision,
   the checkpoint answers the current synchronous population epoch:
   =join_population= if a validated candidate is on file for this
   replica, =poll_population= if already joined and waiting,
   =abstain_population= if nothing valid is on file this epoch
   (examples/lj_cluster_search.rs:5399-5417). This
   ordering is deliberate: a checkpoint often finds the chain mid-hop
   with nothing yet valid, and silence here would starve the epoch
   rather than let it abstain and close without this replica (catalog.org
   "Feynman-Kac population epochs").

5. *Act on a ready population plan.* If the barrier just closed
   (=PopulationSynchronizationOutcome::Ready=,
   examples/lj_cluster_search.rs:5422-5425), the replica locates its
   own destination in the immutable =PopulationEpochPlan=
   (src/methods/feynman_kac.rs:307) via =population_family_position=
   and derives a deterministic rejuvenation draw via
   =population_rejuvenation_draw=
   (examples/lj_cluster_search.rs:5437-5445). If =CATALOG_SHARED_BIAS=
   is =1=, the assigned parent's coordinates are queued for deposit
   into this chain's own bias (=pending_deposits=,
   examples/lj_cluster_search.rs:4291, 5446-5448). Unless
   =CATALOG_COOP_WELLS= is =0=, the parent's SOAP cloud mean is folded
   into the shared featomic packing archive (=set_packing_archive=,
   examples/lj_cluster_search.rs:4284, 5449-5476). The replica no longer
   requests a =boundary_crossing= from the parent's descriptor;
   =population_region_trial= (examples/lj_cluster_search.rs:3275), which
   built the proposal from a returned crossing, is now called only from
   a test. The plan is applied by occupancy instead: the champion
   stays, a kept extra may take a better isomer of the same packing,
   leftover extras reseed, and a deeper different funnel is never
   copied. Each move returns through =population_reconfiguration=
   (examples/lj_cluster_search.rs:5508, 5550, 5612), which records the
   slice and returns =CheckpointAction::BoundaryProposal= immediately,
   skipping the ordinary policy decision below for this checkpoint.

6. *Report a position, ordinary case.* The current state's descriptor
   comes from =crate::descriptor_space::DescriptorSpace::describe=,
   asked at every checkpoint before the population barrier
   (examples/lj_cluster_search.rs:5116-5117). When no population
   reconfiguration fires, the checkpoint calls
   =CooperativeRun::try_policy_input_with_lambda=, which posts the
   request and applies the last answer without waiting
   (=CooperativeRun::policy_input_with_lambda=, which waits for the
   reply, when =CATALOG_SYNC_POLICY= is =1=), then
   =CooperativeRun::decide=
   (examples/lj_cluster_search.rs:4642, 5875-5891, 6004-6006). This is
   deliberately *not* an identity claim: it reports wherever the chain
   stands, mid-hop or not, against the census, with no purity gate --
   only the offer step above (step 3) feeds the identity tier. =decide= runs
   the pure =CatalogPolicy::decide= (catalog.org "catalog policy")
   against the coordinator's returned =CensusEvidence= and
   =ActiveCatalogRelation=.

7. *Act on the policy decision.* =ContinueLocal= does nothing further
   this checkpoint (examples/lj_cluster_search.rs:6245). The other
   actions no longer route through =CooperativeRun::boundary_crossing=,
   which the checkpoint now polls only for a due probe from the current
   state, before the population barrier
   (examples/lj_cluster_search.rs:5152), and only that probe's
   =Crossing= (an observed boundary transport target, catalog.org
   "boundary transport") reaches =boundary_crossing_trial=
   (examples/lj_cluster_search.rs:5149, 5154). Each action asks the
   coordinator for its own target instead. =Exploit= samples the
   incumbent catalog entry (=try_sample_candidate=,
   examples/lj_cluster_search.rs:6246-6250); =Leave= reads several
   catalog entries at once (=try_sample_candidates=,
   examples/lj_cluster_search.rs:6290, 6355) and, when
   =CATALOG_SHARED_BIAS= is =1= and the replica stands on a packing the
   catalog already holds, queues a deposit under its own feet
   (=pending_deposits=, examples/lj_cluster_search.rs:4291, 6377-6381);
   =Explore= asks for a
   descriptor hole (=descriptor_hole=,
   examples/lj_cluster_search.rs:6581-6585). An action that builds a
   proposal returns =CheckpointAction::BoundaryProposal=.

8. *Record the slice trace.* Whatever happened, a =SliceTrace=
   (catalog.org "CooperativeRun composition layer") is recorded via
   =CooperativeRun::record_slice=
   (examples/lj_cluster_search.rs:6015, 6626-6628) before the checkpoint
   returns, so the run's newline-delimited JSON trace
   (=CooperativeRun::json_lines=) has one complete, replayable entry
   per checkpoint regardless of which branch fired.

* Polish and offer

Separately from the checkpoint cadence, =Config.polish_records= extends
the relaxation of any trial that improves the run's *record* (not every
hop) to the shared-catalog convergence tolerance
(src/methods/cluster_hopping/config.rs:894-903). This bounds the extra
cost to the number of record improvements -- a few hundred evaluations
each over tens of events across a campaign budget -- rather than paying
full precision on every accepted hop. Only states polished to this
tolerance are valid offers in step 3 above; a solo (non-cooperative) run
leaves =polish_records = 0= and never pays this cost.

* Population epoch: reconfiguration

When enough replicas have joined a population epoch
(=SynchronousPopulation=, catalog.org "Feynman-Kac population epochs"),
the coordinator ranks the submitted =PopulationMember=s
(=rank_population=), builds the bounded log-weight selection potential
from =SelectionCoefficients=, draws parents by systematic resampling at
a replayable per-epoch offset (=epoch_systematic_offset=), and caps
family sizes (=cap_families=). The resulting =PopulationEpochPlan= is
what step 5 above consumes. Genealogy diagnostics (Kish effective
sample size, unique parents, max/variance of family size) are computed
alongside the plan for later analysis, not consumed by the replica
itself.

* Reconfiguration and back to hopping

After a population reconfiguration or a boundary-crossing proposal is
accepted, the checkpoint returns control to
=run_with_bias_at_checkpoints=, which relaxes the new candidate state
through the ordinary quench and re-enters the hop loop. The chain's own
history (bias deposits, best-known state, tabu list) survives the
reconfiguration; only the *live* state changes. The next checkpoint
resumes at step 1.

* Termination and the run trace

The loop ends when the chain's =Ledger= is spent
(src/methods/cluster_hopping.rs:458). The example writes the complete
=CooperativeRun::json_lines= trace either to =CATALOG_TRACE= or to
standard error (examples/lj_cluster_search.rs:6679-6696); this is the
newline-delimited event stream (catalog.org "CooperativeRun composition
layer") from which every mechanism's contribution to the run can be
replayed after the fact -- which checkpoints offered a candidate, which
were rejected and why (=PolicyReason= codes), which population epochs
this replica joined versus abstained, and the exact charged-work ledger
that makes cross-replica comparisons auditable (catalog.org
"paired-seed evaluation methodology").

A separate, unprivileged observer may poll the coordinator's aggregate
status at any time via =examples/catalog_status.rs=, which calls
=CatalogClient::observer_status= (src/catalog_rpc/client.rs:972) --
the read-only op that needs no replica identity, signature, or journal
entry (catalog.org "Cap'n Proto catalog protocol").

* Corrections and precise terminology

Three points in the narrative above use looser language than the code
supports. Stated precisely, with the =file:line= evidence.

** The five-fold typed design

"Five-fold" names the crate's own component algebra, not a separate
cooperative-layer invention: every chain runs the same typed
=Sampler<T>= point (src/sampler.rs:30) built from five interchangeable
traits, the "IISE manuscript" algebra each trait's own header comment
cites directly:
=Cool : N -> R_>0= (src/cool.rs:1, non-increasing cooling schedule),
=Neigh : S -> 2^S= (src/neigh.rs:1, neighborhood relation, law L1:
symmetric), =Move : S x R_>0 -> Delta(S)= (src/movekernel.rs:1,
temperature-indexed proposal kernel, law L2: support contained in the
neighborhood), =Accept : R x R_>0 -> [0,1]= (src/accept.rs:1,
acceptance rule, law L3: downhill always accepted, law L4: acceptance
non-decreasing in temperature), plus the implicit objective (Obj).
=SaVariant::checked= / =checked_with_sweep= (src/laws.rs:1-7) validate a
concrete tuple of components against all four composition laws, the
first three as Boolean witnesses and all four as executable proptest
sweeps. This is the README's "same five-component algebra" of =Obj=,
=Cool=, =Neigh=, =Move= and =Accept= (README.md:9), named precisely.

** Transport: Cap'n Proto RPC with a single-coordinator journal

There is no nng catalog transport and no raft-style or other
distributed consensus for the catalog: one coordinator process owns
the journal. What is actually there:

- Transport: two-party Cap'n Proto RPC on TCP. =Catalog.capnp=
  defines =Coordinator=, =Session=, and =Subscriber=. A replica
  =attach=es with its identity and a subscriber capability, then
  =Session.call= carries the existing =CatalogRequest= /
  =CatalogReply= payload so journal identity and every operation
  handler stay unchanged. =Coordinator.observe= needs no identity.
- Coordination: =CatalogServer::start= binds one socket and runs a
  single =RpcSystem= accept loop on a dedicated thread with a tokio
  =LocalSet= that owns coordinator state. Candidate validation that
  does not depend on that state runs on a rayon pool and is awaited
  before the request is applied. The coordinator pushes
  =CoordinatorEvent= values to every attached subscriber when an
  epoch closes, when the roster changes, and when a replica retires.
- Durability: a single append-only request journal
  (=append_journal= / =replay_journal=), replayed at startup and keyed
  by =(replica, event_sequence)= so a restarted coordinator recovers
  the same state a live one would have, and a resent request after a
  dropped reply is a no-op rather than a double-charge. This is crash
  recovery for one process, not agreement among several.

Anywhere the narrative above says "the coordinator" it means this: one
process, one LocalSet, one journal. A second coordinator process
pointed at the same journal path would corrupt it; nothing in this
crate arbitrates between two.

** neus_bridge: the bridge layer between chains holding different minima

[[file:catalog.org::*Nonequilibrium-umbrella bridge between two minima (=neus_bridge=)][neus_bridge]]
supplies the machinery of the bridge layer: an image string between
two validated catalog basins, Voronoi-region membership, and
flux-balance weight transfer producing a committor surrogate along
the channel. The wiring was meant to close the loop the other
cooperative mechanisms open, but it no longer starts. The
[[file:catalog.org::*Spectral referee over the explored landscape (=landscape_graph=)][spectral referee]]
names the seam, and =commission_bridge=, which turned the seam's two
best-anchored [[file:catalog.org::*Active basin catalog][catalog]]
entries into a string with region weights and entry lists at the
population epoch boundary, has been removed, so no line holds it; two
protocol operations still serve a bridge to replicas, an assignment
poll (=CatalogOperation::BridgeAssignment=,
src/catalog_rpc/server.rs:1651) and a crossing report
(=CatalogOperation::BridgeCrossing=, src/catalog_rpc/server.rs:1697),
but with no bridge commissioned the poll assigns nothing and every
crossing report is rejected. The run loop, behind the =CATALOG_BRIDGE=
gate (examples/lj_cluster_search.rs:4303), would jump to stored entry
states through the ordinary probe-proposal path and report every
region change of its live descriptor as a crossing. Confinement is soft:
crossings are recorded rather than moves rejected, so no chain's
acceptance rule changes, the boundary both rejected sharing
mechanisms crossed. The mechanism is gated until a paired smoke
measures it, the same discipline every mechanism in
[[file:catalog.org][the catalog]] enters campaigns under.
