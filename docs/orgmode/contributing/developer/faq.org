* Developer FAQ

** Why is cbindgen behind a feature flag?

=cargo publish= forbids build scripts that modify the source directory.
Since =cbindgen= writes =rgpot-core/include/rgpot.h= into the crate tree, it
must be opt-in.
The committed header is the canonical copy; regenerate it with
=pixi r gen-header= when the public Rust API changes.

** Why is the Cap'n Proto schema bundled?

The schema at =rgpot-core/schema/Potentials.capnp= is included in the crate so
that the =schema= feature (and the =rpc= and =profile= features that enable it)
works when installed from =crates.io=, where the monorepo's =CppCore/= directory
is not available.
The =build.rs= tries the bundled copy first, then falls back to
=CppCore/rgpot/rpc/Potentials.capnp= in the monorepo.
When neither exists, it writes an empty stub module instead.

** How do I repin potentials-schema?

Both vendored copies
(=CppCore/rgpot/rpc/Potentials.capnp= and =rgpot-core/schema/Potentials.capnp=)
are the pinned upstream =Potentials.capnp= byte for byte.
A parent project such as gpridge resolves =potentials-schema= from its own wrap
and compares the copies with that file, so the wrap carries no =diff_files=.
Change =revision= and =directory= in =subprojects/potentials-schema.wrap= and
copy the upstream file over both copies.
Then append the new ordinals to =CppCore/rgpot/rpc/Potentials.ordinals=:

#+attr_rgpot: syntax fetches the pinned schema over the network
#+begin_src bash
python3 CppCore/rgpot/rpc/schema_ledger.py append
python3 CppCore/rgpot/rpc/schema_ledger.py check --fetch --base origin/develop
#+end_src

The ledger is append only.
=check= fails when a line changes, moves or disappears relative to =--base=,
when the pinned schema renumbers, retypes or drops a recorded ordinal, when a
vendored copy is not the pinned file, and when the effective schema disagrees
with the ledger.
Ordinals belong to potentials-schema: add a new field or arm there first, then
repin.
The =schema_ledger= job of =CI (orchestrator)= runs this check with =--fetch=
and, when the base commit is available, =--base= set to the pull request base.
The meson =schema= suite runs it too, and with the =potentials-schema=
subproject also =schema-sync-canonical-rpc= and =schema-sync-canonical-core=
against that checkout.

** How do I add an rgpot-local schema field?

Only when upstream cannot take it yet.
Write a diff against the vendored copy that only adds lines, put it in
=CppCore/rgpot/rpc/local/=, append its name to
=local/series=, and copy both files to =rgpot-core/schema/local/=.
Leave the vendored copies alone.
=schema_ledger.py append= then records each new ordinal as =local=:

#+attr_rgpot: syntax fetches the pinned schema over the network
#+begin_src bash
python3 CppCore/rgpot/rpc/schema_ledger.py append
python3 CppCore/rgpot/rpc/schema_ledger.py check --fetch --base origin/develop
python3 CppCore/rgpot/rpc/schema_ledger.py apply --out build/Potentials.capnp
#+end_src

A series diff may not remove or rewrite a line that carries an =@N= ordinal, and
every ordinal it adds must be a =local= ledger entry that upstream does not
declare.
Meson, CMake and =rgpot-core/build.rs= compile, install and serve the effective
schema, the vendored copy with the series applied; =apply= writes the same file.
When upstream later adopts the field unchanged, repin, drop it from the series
and run =append=: the =local= line stays and a later =upstream= line for the
same ordinal retires it.
=check= refuses the repin until that is done.

** Why is the crate README in org-mode?

The source of truth is =rgpot-core/README.org=.
It is exported to =rgpot-core/README.md= via =pixi r -e docs gen-readme= (which
uses Emacs =ox-md=).
The rendered markdown is committed and referenced by =Cargo.toml= for display on
crates.io.
Edit the =.org= file, then regenerate.
Both files carry the version in cogapp markers, so run
=pixi r -e version release-cog= after a version change.

** How do I add a new pixi environment?

Edit =pixi.toml=: add a feature section with its dependencies, then register it
in =[environments]=.
See the existing =rpc=, =itests= and =docs= features, and the =rpctest=
environment that combines =rpc= and =itests=, as examples.
Give a new environment that builds the project its own CI job, as the
[[file:index.org][Developer Guide]] explains.

** Where does the Rust API documentation come from?

The Sphinx extension =sphinxcontrib-rust= parses the Rust source directly
(=rgpot-core/src/=) and generates RST during =sphinx-build=.
The output goes to =docs/source/crates/rgpot_core/= and is included in the main
documentation site alongside the C++ API reference.

** How do I run a single Rust test?

#+attr_rgpot: syntax compiles the Rust crate
#+begin_src bash
cargo nextest run --manifest-path rgpot-core/Cargo.toml -E 'test(test_name)'
#+end_src

Or with standard =cargo test=:

#+attr_rgpot: syntax compiles the Rust crate
#+begin_src bash
cargo test --manifest-path rgpot-core/Cargo.toml -- test_name
#+end_src
