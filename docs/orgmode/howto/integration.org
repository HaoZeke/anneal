* External Integration Guide

This guide describes how to integrate ~rgpot~ into external codebases,
particularly legacy projects with their own type systems.
It covers the namespace collision problem, the recommended mitigation
strategies, and a worked example using [[https://github.com/TheochemUI/eOn]
[eOn]] as a concrete case study.

** The Namespace Collision Problem

Legacy atomistic codes often declare =Potential= and =AtomMatrix= at global
scope.
The C++ library of ~rgpot~ keeps both names inside =namespace rgpot=:

- =AtomMatrix= :: A lightweight row-major matrix class,
  =rgpot::types::AtomMatrix= (=CppCore/rgpot/types/AtomMatrix.hpp=).
=CppCore/rgpot/Potential.hpp= uses it as =types::AtomMatrix= inside
=namespace rgpot= and declares no =using= at global scope.
- =Potential= :: =rgpot::Potential<Derived>= and =rgpot::PotentialBase= live in
  =namespace rgpot=.

The Cap'n Proto schema is the part that still collides.
=CppCore/rgpot/rpc/Potentials.capnp= has no =$Cxx.namespace= annotation.
The generated =Potentials.capnp.h= therefore declares =Potential= (from
=interface Potential=), =ForceInput=, =PotentialResult=, =PotentialConfig= and
the other schema types at global scope.
This collides with any consumer that defines its own =class Potential= or
=ForceInput= at global scope.

The =PotentialConfig= arms that carry backend parameters over RPC are listed in
[[file:../reference/potential_config.org][PotentialConfig arms]].

For example, [[https://github.com/TheochemUI/eOn][eOn]] defines:

- =AtomMatrix= :: A typedef for =Eigen::Matrix<double, Eigen::Dynamic, 3>=.
- =class Potential= :: The base class for all eOn potential energy surfaces.

Including both eOn's =Potential.h= and =Potentials.capnp.h= in the same
translation unit fails to compile.
Including =rgpot/Potential.hpp= next to eOn's headers does not bring a second
global =AtomMatrix= or =Potential=.
This translation unit compiles:

#+attr_rgpot: compile
#+begin_src cpp
// Consumer types at global scope.
class Potential {
public:
  virtual ~Potential() = default;
};
using AtomMatrix = int;

#include "rgpot/LennardJones/LJPot.hpp"

int main() {
  rgpot::LJPot lj;
  AtomMatrix a = 0;
  return a;
}
#+end_src

** Mitigation Strategies

*** Strategy 1: Namespace the consumer's types

If the consuming codebase can be refactored, placing its types inside a project
namespace eliminates collisions entirely:

#+attr_rgpot: fragment
#+begin_src cpp
// Instead of global scope:
class Potential { ... };
using AtomMatrix = Eigen::Matrix<double, Eigen::Dynamic, 3>;

// Use a project namespace:
namespace eon {
class Potential { ... };
using AtomMatrix = Eigen::Matrix<double, Eigen::Dynamic, 3>;
} // namespace eon
#+end_src

This is the cleanest solution but requires touching every file in the consumer
codebase -- impractical for large legacy projects.

*** Strategy 2: Separate translation units (for legacy codes)

When the consumer cannot be easily modified, use separate translation units
(TUs) so the consumer's =Potential= and the generated capnp header never appear
together:

#+attr_rgpot: skip layout sketch of two translation units, not compilable code
#+begin_example
TU 1 (ConsumerBridge.cpp):
  #include "consumer/Potential.h"    // consumer's Potential
  // Wraps consumer types into a flat-array callback

TU 2 (RpcServer.cpp):
  #include "Potentials.capnp.h"       // capnp's Potential
  // Implements the RPC server using only flat arrays
#+end_example

The two TUs communicate through a type-free interface such as a =std::function=
over flat C arrays, avoiding any shared header that contains either =Potential=.

*** Strategy 3: RPC-client-only linking

For consumers that only need the Cap'n Proto schema, link only the schema
library (=ptlrpc_dep= in meson) rather than the full =rgpot_dep=.
This avoids pulling in =librgpot= and the C++ potentials.
It does not avoid the global names of =Potentials.capnp.h=, so it combines with
Strategy 2.

In meson:

#+attr_rgpot: fragment
#+begin_src meson
rgpot_proj = subproject('rgpot', default_options: ['with_rpc_client_only=true'])
ptlrpc_dep = rgpot_proj.get_variable('ptlrpc_dep')
# Only capnp schema + generated code, no rgpot types
#+end_src

=ptlrpc_dep= links a static convenience archive, so this strategy costs the
consumer no extra shared object.
Take =ptlrpc_hdr_dep= instead in any static library of your own that another of
your static libraries also links, or both end up carrying the generated
translation unit.

** Flat-Array Callback Pattern

The recommended integration pattern for legacy codes is a flat-array callback
that requires no shared types between the consumer and rgpot:

#+attr_rgpot: compile
#+begin_src cpp
#include <functional>

// ForceCallback: a std::function over flat C arrays
using ForceCallback = std::function<void(
    long nAtoms,
    const double *positions,   // [nAtoms * 3], row-major
    const int *atomicNrs,      // [nAtoms]
    double *forces,            // [nAtoms * 3], output
    double *energy,            // scalar, output
    const double *box          // [9], row-major 3x3
)>;
#+end_src

This signature maps directly to the Cap'n Proto =ForceInput= / =PotentialResult=
schema without requiring any Eigen, AtomMatrix, or =rgpot::ForceInput= types.
The callback is created in the consumer's TU (which sees the consumer's types)
and passed to the RPC server TU (which sees the capnp types).
Neither TU needs to include the other's headers.

*** Data layout

All arrays use the same flat layout as the Cap'n Proto schema:

| Array | Layout | Size |
|-------+--------+------|
| Positions | =[x1,y1,z1, x2,y2,z2, ...]= | =nAtoms * 3= |
| Atomic numbers | =[Z1, Z2, ...]= | =nAtoms= |
| Box | =[ax,ay,az, bx,by,bz, cx,cy,cz]= | =9= |
| Forces | =[Fx1,Fy1,Fz1, ...]= | =nAtoms * 3= |

This is row-major and matches the convention used by both the Rust core
(=rgpot_force_input_t=) and the existing C++ potentials (=ForceInput=).

** Worked Example: eOn

[[https://github.com/TheochemUI/eOn][eOn]] is a saddle-point search framework
with its own =class Potential= and =AtomMatrix= (Eigen-based) at global scope.
Its serve mode exposes eOn potentials through rgpot's Cap'n Proto =Potential=
interface using the two-TU + flat-array pattern.
The code below is from the eOn tree, not from this repository.

*** Architecture

#+attr_rgpot: skip ASCII diagram of the two eOn translation units
#+begin_example
+---------------------------+     +---------------------------+
| ServeMode.cpp (TU 1)      |     | ServeRpcServer.cpp (TU 2) |
|                           |     |                           |
| #include "Potential.h"    |     | #include "Potentials.capnp.h"
| (eOn's Potential class)   |     | (capnp's Potential iface) |
|                           |     |                           |
| makeForceCallback(pot)    |---->| startRpcServer(callback)  |
|   wraps pot->force()      |     |   unwraps capnp structs   |
|   into ForceCallback      |     |   calls callback(...)     |
+---------------------------+     +---------------------------+
           |                                    |
           |    ForceCallback (flat arrays)      |
           +------------------------------------+
                      No shared types
#+end_example

*** TU 1: ServeMode.cpp

This file includes eOn's =Potential.h= and wraps any eOn potential into a
=ForceCallback=:

#+attr_rgpot: skip eOn source; needs eOn's Potential.h, Parameters and helper_functions
#+begin_src cpp
#include "Potential.h"       // eOn's Potential, AtomMatrix
#include "ServeRpcServer.h"  // ForceCallback typedef only

namespace {
ForceCallback makeForceCallback(std::shared_ptr<::Potential> pot) {
  return [pot = std::move(pot)](long nAtoms, const double *positions,
                                const int *atomicNrs, double *forces,
                                double *energy, const double *box) {
    double variance = 0.0;
    pot->force(nAtoms, positions, atomicNrs, forces, energy, &variance, box);
  };
}
} // anonymous namespace

void serveMode(const Parameters &params, const std::string &host,
               uint16_t port) {
  auto eon_pot = helper_functions::makePotential(params);
  auto callback = makeForceCallback(std::move(eon_pot));
  startRpcServer(std::move(callback), host, port);
}
#+end_src

*** TU 2: ServeRpcServer.cpp

This file includes the capnp-generated header and implements the RPC server.
It never includes eOn's =Potential.h=.
The capnp list readers returned by =getPos()=, =getAtmnrs()= and =getBox()= are
not C arrays, so the server copies them into vectors before the callback:

#+attr_rgpot: fragment
#+begin_src cpp
#include "Potentials.capnp.h"   // capnp's Potential interface
#include "ServeRpcServer.h"     // ForceCallback typedef

#include <vector>

class CallbackPotImpl final : public Potential::Server {
  ForceCallback m_callback;
public:
  explicit CallbackPotImpl(ForceCallback cb)
      : m_callback(std::move(cb)) {}

  kj::Promise<void> calculate(CalculateContext ctx) override {
    auto fip = ctx.getParams().getFip();
    // A capnp list reader is not a C array; copy it out.
    auto copy = [](auto list) {
      std::vector<std::decay_t<decltype(list[0])>> out(list.size());
      for (unsigned i = 0; i < list.size(); ++i) {
        out[i] = list[i];
      }
      return out;
    };
    const std::vector<double> pos = copy(fip.getPos());
    const std::vector<int32_t> atmnrs = copy(fip.getAtmnrs());
    const std::vector<double> box = copy(fip.getBox());

    long nAtoms = static_cast<long>(atmnrs.size());
    std::vector<double> forces(nAtoms * 3, 0.0);
    double energy = 0.0;

    // Call through the flat-array callback -- no eOn types here
    m_callback(nAtoms, pos.data(), atmnrs.data(),
               forces.data(), &energy, box.data());

    auto result = ctx.getResults().initResult();
    result.setEnergy(energy);
    auto fout = result.initForces(forces.size());
    for (size_t i = 0; i < forces.size(); ++i) {
      fout.set(i, forces[i]);
    }
    return kj::READY_NOW;
  }
};
#+end_src

*** Bridge header: ServeRpcServer.h

The bridge header defines only the =ForceCallback= type and the server entry
points.
It includes neither eOn nor capnp headers:

#+attr_rgpot: compile
#+begin_src cpp
#pragma once
#include <functional>
#include <string>
#include <vector>
#include <cstdint>

using ForceCallback = std::function<void(
    long nAtoms, const double *positions, const int *atomicNrs,
    double *forces, double *energy, const double *box)>;

void startRpcServer(ForceCallback callback,
                    const std::string &host, uint16_t port);
void startPooledRpcServer(std::vector<ForceCallback> pool,
                          const std::string &host, uint16_t port);
#+end_src

*** Build system integration

eOn pulls rgpot as a meson subproject with =with_rpc_client_only=true=, linking
only the capnp schema dependency:

#+attr_rgpot: fragment
#+begin_src meson
rgpot_proj = subproject('rgpot',
    default_options: ['with_rpc_client_only=true'])
ptlrpc_dep = rgpot_proj.get_variable('ptlrpc_dep')

serve_sources = ['ServeMode.cpp', 'ServeRpcServer.cpp']
# ptlrpc_dep provides capnp schema; no rgpot types linked
#+end_src

*** Running the server

#+attr_rgpot: skip eonclient commands from the eOn tree
#+begin_src bash
# Serve a Lennard-Jones potential on port 12345
eonclient --serve "lj:12345"

# Serve a Metatomic ML potential
eonclient --serve "metatomic:12345" --config model.ini

# Multiple potentials concurrently
eonclient --serve "lj:12345,metatomic:12346" --config model.ini

# Gateway mode: single port, pooled instances
eonclient -p metatomic --serve-port 12345 --replicas 4 --gateway \
    --config model.ini
#+end_src

Any rgpot-compatible client (Julia, Python, C++) can then connect:

#+attr_rgpot: skip ChemGP Julia client, not part of this repository
#+begin_src julia
# Julia (ChemGP)
using ChemGP
pot = RpcPotential("localhost", 12345,
                   Int32[29, 29], Float64[20,0,0, 0,20,0, 0,0,20])
E, F = calculate(pot, Float64[0,0,0, 2.2,0,0])
#+end_src

** Summary of Approaches

| Approach | Effort | When to use |
|----------+--------+-------------|
| Namespace consumer types | High (consumer refactor) | Greenfield projects or major rewrites. |
| Separate TUs + flat callback | Medium (build system) | Legacy codes with global-scope types next to =Potentials.capnp.h=. |
| RPC-client-only linking | Low (build option) | Consumer needs the schema (client or server stubs) but not =librgpot=. |

For legacy codebases like eOn where refactoring all types into a namespace is
impractical, the two-TU + flat-array callback pattern provides an integration
path with no modifications required to either rgpot or the consumer's existing
type system.
